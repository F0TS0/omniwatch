# Product flow

1. The visitor arrives at `/`, a compact browser-signal dossier (`components/SelfDossier.tsx`). OmniWatch automatically reads six browser-visible categories: timezone, language, browser environment, screen context, device capability, and network type. Raw browser signal values remain local.
2. The visitor selects a hypothetical target behaviour and presses "TRAIN CLASSIFICATION." Built-in choices use the deterministic local definition in `lib/classification.ts`. A custom event is sent, with only generic signal-category names and no raw browser values, to the server-side Groq route. The response keeps surface-language classification separate from browser-category relevance: explicit violent wording can be flagged without claiming intent or credibility, while only `MODERATE` or `STRONG` category assessments count as materially relevant. `lib/custom-event.ts` calculates a browser-context relevance score locally with no points for merely observing ordinary signals or activating the policy. If this analysis is unavailable, the UI says so and does not fabricate a custom score.
3. A "YOU HAVE DONE NOTHING WRONG" / "OBSERVATION IS NOT ENFORCEMENT" transition appears, with a single primary action: "TEST PERFECT ENFORCEMENT," linking to `/enforcement`.
4. `/enforcement` shows the visitor's own dossier continuity (dossier ID, observed signal count, classification status), lets them pick an intervention threshold (50–90%, default 70%), and lists Martin Luther, 1517 as the only runnable historical test case (Philadelphia 1776 and Estonia 1988 are listed as "NOT YET AVAILABLE" and are not clickable). "BEGIN TEST" carries this configuration into the historical case via `sessionStorage` (`lib/operator-context.ts`).
5. `/case/luther-1517` runs the existing deterministic simulation (`lib/simulation.ts`, `components/Simulation.tsx`), revealing one signal at a time. A "SYSTEM POLICY" panel shows the visitor's own configured threshold and dossier continuity throughout.
6. Once a signal's confidence meets the visitor's chosen threshold (not a fixed 70%), the status becomes `PENDING_INTERVENTION` (or the curated final `INTERVENTION_RECOMMENDED` state) and the visitor is told "YOUR POLICY THRESHOLD HAS BEEN REACHED" — they choose to intervene or continue observation. Until that point it remains `MONITORED`, even if the canonical 70% policy would already have crossed. The curated Luther confidence sequence (8, 22, 45, 71, 89, 94) is never recalculated; only which of those existing values first meets the chosen threshold changes.
7. Intervening produces the existing authorisation record and the curated counterfactual outcome ("Publication prevented").
8. A final reveal follows directly on the outcome page: "DID THE SYSTEM FAIL? No." — the system observed, classified, and intervened exactly as designed; the outcome is presented as a design success with a disastrous societal cost, not a malfunction.

`/cases` and `/present` still exist as secondary, standalone routes (a plain case archive, and an anonymous present-day illustrative timeline), but neither is part of the primary flow above.
